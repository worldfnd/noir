# Field genericity

Field metadata, source checks, and monomorphization use a [`FieldConfig`](../acvm-repo/acir_field/src/field_config.rs) chosen once per compilation (`--field`, default: the field the compiler is built with). The `goldilocks` feature of [`noirc_driver`](../compiler/noirc_driver/Cargo.toml) selects the field the compiler is *built* with, Goldilocks (p = 2^64 − 2^32 + 1) or bn254 by default; that field is the one the back half lowers into, and the front half runs under any configured field in the same binary. Under bn254 every Noir integer fits in one field element, so field arithmetic can carry integers without loss; under Goldilocks a `u64` can exceed p, so anything that carries an integer through the field silently corrupts it. The rules below say where integers must be carried exactly, where a value is reduced, and where an out-of-field value is an error. They hold under every supported field, and the tests that pin them run under both builds.

# The value rules

1. **Casts.** `x as Field` is the identity on the value and is defined only for source types whose every value lies below p: `bool`, `Field`, and an unsigned integer type narrower than the field (`FieldConfig::fits_unsigned`). An unsigned type that can hold a value at or above p (`u64` and `u128` under Goldilocks) is refused at type check (`IntegerTypeExceedsField` in [`types`](../compiler/noirc_frontend/src/elaborator/types.rs)), whatever value it holds at run time, so whether a program compiles depends on the field. The escape hatch is an explicit narrowing cast, `(x as u32) as Field`, which keeps one uniform meaning for `as Field` under every field. Reduction modulo p is rejected because it makes the cast non-injective (`x as Field == y as Field` for `x != y`), and a run-time range check is rejected because it costs a constraint on every non-constant cast. Casting a signed integer to `Field` directly is a type error (`UnsupportedFieldCast`), so a negative value reaches `Field` only through its unsigned reinterpretation: `(-1i8 as u8) as Field == 255`, never `p - 1`. An integer-to-integer cast keeps the low bits of the target width and reads them by the target's signedness, without any intermediate field value, so a `u64` above p survives `as u128` unchanged. The comptime interpreter's [`cast`](../compiler/noirc_frontend/src/hir/comptime/interpreter/cast.rs) module implements this on `BigInt` and refuses, rather than reduces, a pattern at or above p (`field_casts_are_exact_or_refused`); `casts_follow_the_bit_pattern_model_at_every_width` checks it against a bit-pattern model and `integer_casts_do_not_reduce_modulo_the_field` pins the integer-to-integer direction. The type checker applies the rule where the cast is written, which is too early when the source is a type variable that inference binds later, as in a closure `|v| v as Field` passed to a generic function; the monomorphizer therefore checks every cast to `Field` again once its source type is concrete (`check_cast_to_field` in [`monomorphization`](../compiler/noirc_frontend/src/monomorphization/mod.rs), reported as `InvalidFieldCast` with the type checker's own diagnostic). In [`field_contract`](../compiler/noirc_frontend/src/tests/field_contract.rs), `casts_to_field_are_refused_when_the_type_can_exceed_the_modulus`, `comptime_casts_to_field_follow_the_same_rule`, `casts_to_field_through_an_inferred_type_follow_the_same_rule`, `signed_casts_to_field_through_an_inferred_type_are_refused`, `narrowing_before_a_field_cast_is_accepted_under_every_field` and `comptime_casts_wrap_to_the_target_width` pin the rule through the language, under every configuration where the rule is a type error including comptime evaluation.
2. **Canonical `Field` values error, never wrap.** A `Field` literal must lie in `[0, p)` of the configured field (`check_integer_literal_fits_its_type` in [`lints`](../compiler/noirc_frontend/src/elaborator/lints.rs), pinned for every configuration by `field_literals_must_be_canonical`), and converting a `BigInt` whose magnitude is not below p into a field value is refused (`FieldValue::try_from_bigint` in [`field_value`](../acvm-repo/acir_field/src/field_value.rs)). These conversions reject noncanonical magnitudes instead of reducing them.
3. **Integer literals are exact.** Integer types up to `u128` are legal under every field and the monomorphized AST carries their values exactly as `BigInt` literals, however narrow the field (`integer_literals_above_the_modulus_stay_exact`). The lexer's ceiling is the field-independent `2^256 - 1` (`test_int_too_large`); the per-type bound is applied at type-check. The back half of the compiler reduces these values through the field; a consumer of the monomorphized AST lowers them natively.
4. **Integer arithmetic is checked.** `+`, `-`, `*`, `/`, `%` and negation report overflow instead of wrapping, at every width (`attempt_to_add_with_overflow_at_comptime` in [`metaprogramming`](../compiler/noirc_frontend/src/tests/metaprogramming.rs); the operator impls in [`integer`](../compiler/noirc_frontend/src/hir/comptime/integer.rs) are per-width `checked_*` calls). Casts wrap and arithmetic does not; neither rule is adjusted toward the other.

# Field gating

`#[field(<name or modulus>)]` restricts an item to one field. The argument is a field name (`bn254`, `bls12_381`, `goldilocks`) or a modulus in decimal or `0x` hexadecimal, compared with the configured field by `FieldConfig::matches_field_attribute` (`is_gated_out` in [`dc_mod`](../compiler/noirc_frontend/src/hir/def_collector/dc_mod.rs)). An item gated to another field is dropped during definition collection, before anything about it is interned: it is never name-resolved or type-checked, so its field-specific constants never meet rule 2 and its callees need not exist. Two same-named items gated to different fields therefore coexist, so a library can ship one implementation per field.

The gate applies to free functions, globals, `impl` blocks, the methods inside an `impl`, trait impls (as whole blocks only, since dropping a single method would leave the impl incomplete), inline modules, `mod x;` declarations, and the `impl` blocks and trait impls generated by comptime attribute functions. A gated-out `mod x;` is skipped before its file is looked up, so the file need not exist for the other field; if it does exist, nothing in it is reported, not even a parse error. An inline `mod x { .. }` body is part of its enclosing file and must still parse. The attribute is kept on `TypeImpl` and `NoirTraitImpl` in [`ast::traits`](../compiler/noirc_frontend/src/ast/traits.rs) and printed by the formatter. [`field_attribute`](../compiler/noirc_frontend/src/tests/field_attribute.rs) pins every position under both builds and, in `one_build_gates_by_the_configured_field`, that one binary gates by the configuration rather than by the field it is built with; the [`field_attribute`](../test_programs/execution_success/field_attribute/src/main.nr) program covers the end-to-end case.

# Standard library conversions into `Field`

Rule 1 makes a stdlib item that casts a wide unsigned type to `Field` a compile error under a narrow field, so such items exist only where the type fits. The `From<u64>` and `From<u128>` impls for `Field` in [`convert`](../noir_stdlib/src/convert.nr), the `Hash` impls for `u64`, `u128` and `i64` in [`hash`](../noir_stdlib/src/hash/mod.nr), and the wrapping arithmetic on `u64`, `u128` and `i64` in [`arith`](../noir_stdlib/src/ops/arith.nr) (implemented through the field, so it cannot be correct on a field narrower than the type) carry `#[field(bn254)]`. The gate names a field rather than a width because `#[field]` has no width predicate; the comptime-generated `AsPrimitive<Field>` impls in `convert`, which run code at compile time, use the width directly and skip every type with `bits >= modulus_num_bits()`. A program that converts a `u64` into `Field` under Goldilocks therefore fails with a missing impl rather than compiling to a reduced value.

The `bn254` submodule of [`field`](../noir_stdlib/src/field/mod.nr) is bn254-only by construction (it decomposes the modulus into 128-bit limbs) but is elaborated under every field, because `Field::lt` selects it at run time rather than by gate; its errors under other fields are tolerated. `stdlib_never_casts_a_wide_integer_to_field` and `stdlib_conversions_into_field_follow_the_field_width` in the driver's [`stdlib_field_casts`](../compiler/noirc_driver/tests/stdlib_field_casts.rs) pin both halves under both builds.

# Entry-point values: one field element per scalar

The ABI encodes every scalar (`Field`, integer, `bool`) as exactly one field element (`AbiType::field_count`), so a value can cross the entry-point boundary only if its encoding is a field element. The rule, applied by `scalar_to_field` in the [input parser](../tooling/noirc_abi/src/input_parser/mod.rs): an integer is accepted iff it lies in the range of its type **and** its unsigned fixed-width bit pattern is below p; a `bool` is `0` or `1`; a `Field` is any value below p, a negative native spelling denoting the negation of its magnitude while a quoted spelling must be non-negative. This is a partial value domain, not a ban on wide types: under Goldilocks an `i64` accepts exactly `[-2^63, -2^32] ∪ [0, 2^63 - 1]`, because `-2^32` encodes as `p - 1` and `-1` as `2^64 - 1 ≥ p`. Nothing is ever reduced at this boundary, so accepted signed values never collide modulo p, and in-circuit types are not limited by p at all (rule 3).

`Format::parse` owns the check for both formats and for quoted and native spellings alike, because consumers other than `nargo` stop there and never reach `Abi::encode`; `find_type_mismatch` repeats the type-range half for callers that build an `InputValue` directly. `signed_values_are_accepted_iff_their_bit_pattern_is_below_the_modulus`, `unsigned_values_must_fit_their_width_in_every_spelling`, `unsigned_values_are_accepted_iff_below_the_modulus`, `boolean_values_must_be_zero_or_one_in_every_spelling` and `negative_field_values_are_negated_natively_and_rejected_quoted` pin the domain under both builds.

A multi-element encoding for integers wider than the field is a separate, versioned policy to be agreed with the consumers of the monomorphized AST (signedness, limb width and order, element count, version). The field's properties do not pre-commit it: there is no "elements per integer" property anywhere in the compiler.

# Run-time field configuration

[`FieldId`](../acvm-repo/acir_field/src/field_config.rs) names a supported field: `bn254`, `goldilocks`, and `bls12_381`. Its discriminant is the wire code, decoded only through the checked `from_code`, and it has no `Default`, so a field is always named deliberately. `FieldConfig` holds an id and answers every question the front half asks about its field (`modulus`, `num_bits`, `fits_unsigned`, whether a `width`-bit unsigned type is carried in one element, and `matches_field_attribute`) from rows written out in that file, deliberately not from the `FieldElement` alias the crate is built with, so a bn254 build answers Goldilocks queries. Each row-dependent accessor is an exhaustive `match` with no fallthrough arm, so a new field is a compile error until it has a row (`every_row_states_its_modulus_and_width`), and `the_linked_row_agrees_with_the_linked_field_element` pins the row of the built field to the linked element under whichever field the crate is built with. Two rules keep the front half field-generic: a layer only asks the configuration (modulus, width, whether a width fits) and never names a field or compares against a width literal; and a layer never uses `FieldElement` as the carrier for a value that is not semantically a `Field`.

The configuration is seeded once per compilation. It travels from `--field` on [`CompileOptions`](../compiler/noirc_driver/src/lib.rs) through `FrontendOptions` into the [`NodeInterner`](../compiler/noirc_frontend/src/node_interner/mod.rs), the one object every pass from definition collection to monomorphization holds, at the first elaboration entry point (`collect_defs_and_elaborate` and `Elaborator::new`); a query before that, or a second seed with a different field, is an internal error. Definition collection, the literal lint, the cast rules, the comptime and monomorphization `modulus_*` builtins and the comptime cast widths all read `interner.field()`, and frontend tests compile and execute comptime code under any row in one build (`GetProgramOptions::for_field`).

The monomorphizer's `into_output` returns a `MonomorphizationOutput`: the program, the `FieldId` it was compiled under, and the source files it drew code from. The label travels beside the program, never inside it, and consumers must check it before lowering (`output_is_labeled_with_the_configured_field`).

# Comptime values carry their field

A comptime `Field` value is a [`FieldValue`](../acvm-repo/acir_field/src/field_value.rs): a canonical representative in `[0, p)` together with its `FieldId`. `Integer::Field` uses this carrier for interpreter evaluation and type-level arithmetic. Operations reduce modulo the configured field; mixing fields is an internal error. Native integer variants keep their checked arithmetic.

Tests compare arithmetic, formatting and signed conversions against the linked `FieldElement` at random and boundary values. BN254 hashing also stays compatible because compile-time reflection exposes it. Signed conversions choose by bit length; `Display` chooses by decimal length. The linked-element helpers in [`integer`](../compiler/noirc_frontend/src/hir/comptime/integer.rs) remain for SSA lowering and the fuzzer. `FieldValue::from_linked_element` converts values coming from linked carriers such as the ABI parser.

# Builtin capabilities

`FieldConfig::embedded_curve` and `has_poseidon2_permutation` control the comptime crypto builtins. BN254 supports both; other fields return `Unimplemented`. The solvers use explicit bn254 elements, independent of the compiler's linked field. `poseidon2_config_state_size` still returns bn254's width; fencing this stdlib dependency remains future work. Compile-time hashes are reduced into the configured field and need not agree across fields.

# The backend boundary

`ensure_field_is_linked` in [`noirc_driver`](../compiler/noirc_driver/src/lib.rs) rejects unsupported fields before circuit compilation, including cached artifacts. The same guard protects `nargo execute --force-comptime`, `nargo interpret` and the SSA-impact example, whose ABI or evaluator values still use the linked field. `check_crate` accepts any configured field. Full `nargo check --field goldilocks` still encounters bn254 assumptions in the standard library; isolated frontend and driver tests exercise the supported boundary without those dependencies.

ABI-tagged globals preserve canonical `Field` values and native integer magnitudes. Hex output is padded to the configured element width; wider integers retain their full magnitude, and signed integers carry their sign separately (`abi_tag_integers_preserve_sign_width_and_magnitude`).

The `bn254`, `bls12_381` and `goldilocks` features of [`acir_field`](../acvm-repo/acir_field/src/lib.rs) select the built field and are mutually exclusive (`assert_unique_feature!`), so enabling two is a compile error rather than a silent pick; `FieldId::linked` is the one place the front half reads them. Every crate that reaches the field through the `FieldElement` alias, including [`noirc_abi`](../tooling/noirc_abi/Cargo.toml), forwards a `goldilocks` feature to it. Field element conversions are width-agnostic: `to_i128` reads the shorter of an element's two spellings, on the 8-byte Goldilocks representation as on bn254's 32 bytes (`test_to_i128_roundtrip` and its `goldilocks` twin in [`field_element`](../acvm-repo/acir_field/src/field_element.rs)).

`nargo_cli` and the wasm crates hard-enable `bn254`, so the Goldilocks build is exercised by [its own workflow](../.github/workflows/goldilocks.yml): it builds `noirc_driver` with the feature and runs what only that build can check, the field crate's arithmetic, the configuration row and the run-time carrier against the linked element, the ABI's linked-field parser, the driver's boundary rule, and the SSA probes in [`small_field_validation`](../compiler/noirc_evaluator/src/ssa/interpreter/small_field_validation.rs). The per-field frontend tests need no second build: they compile under every row in one binary. A change to feature-gated code is covered only if a test runs there; the default build proves nothing about it. [The fork-residual workflow](../.github/workflows/fork-residual.yml) compares the fork's diff against the upstream release named in `.github/fork-base.txt` with the committed `.github/fork-residual.txt`, so a file enters or leaves the fork's residual only together with the manifest.

# Checking the two fields against each other

The monomorphized AST is the surface compared across fields: integer, boolean and structural results must agree exactly and only `Field`-typed values may differ; a panic or internal error under either field never passes. The [ast-interpreter](https://github.com/worldfnd/ast-interpreter) executes the AST under both builds of a pinned compiler revision and records the comparison per program in its committed `STATUS.md`.

# Intended direction

The ABI codec validates and converts against the configured field rather than the linked one, which is what still holds `nargo execute --force-comptime` to the built field; the SSA interpreter's numeric values follow, and the ast-interpreter's values take the field at run time from the label the monomorphized output carries. Gating extends to struct and trait definitions and gains a negated form and a width predicate, so a conversion defined for every type that fits below p need not name a field; the standard library compiles under Goldilocks with its bn254-only cryptography fenced and with wrapping arithmetic on wide types implemented natively rather than through the field; and a second arithmetic backend makes the back half itself field-generic, at which point the boundary rule has nothing left to refuse.
