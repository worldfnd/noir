# Field genericity

Field metadata, source checks, and monomorphization use a [`FieldConfig`](../acvm-repo/acir_field/src/field_config.rs) chosen once per compilation (`--field`, default: the field the compiler is built with). The `goldilocks` feature of [`noirc_driver`](../compiler/noirc_driver/Cargo.toml) selects the field the compiler is *built* with, Goldilocks (p = 2^64 − 2^32 + 1) or bn254 by default; that field is the one the back half lowers into, and the front half runs under any configured field in the same binary. Under bn254 every backend-supported integer fits in one field element, so field arithmetic can carry integers without loss; under Goldilocks a `u64` can exceed p, so anything that carries an integer through the field silently corrupts it. The rules below say where integers must be carried exactly, where a value is reduced, and where an out-of-field value is an error. They hold under every supported field, and the tests that pin them run under every field configuration in one build. An entry point's values carry no field at all: they cross as bytes, the same on every field (see the entry-point section).

# The value rules

1. **Casts and conversions.** A value crosses between `Field` and an integer type through a conversion that says what happens to a value that does not fit, not through `as`.
   - **The rule.** `as` between `Field` and an integer type is an error in every crate, the standard library included (`FieldCastDenied`, decided by `field_cast_error` in [`function_context`](../compiler/noirc_frontend/src/elaborator/function_context.rs)): in either direction, for signed and unsigned types, at every width and under every field, so whether a program compiles does not depend on the field. The cast is judged once its source type is known, at the end of the function, global or `comptime` block it is written in. A closure parameter is judged as the type inference binds it to and an untyped variable as the `Field` it defaults to (`the_denial_follows_inference`); a cast in a macro argument whose source the enclosing function binds later is judged there (`a_cast_in_a_macro_argument_is_denied_once_its_source_is_bound`). An integer literal that its target type holds as written is exempt, since it is the same number under every field (`a_literal_that_fits_its_target_may_be_cast`); where the target's width names a generic, the literal must fit the narrowest legal width, `0..=3` unsigned and `0..=1` signed, so it holds at whatever width the generic is bound to (`a_literal_that_fits_every_width_may_be_cast_to_a_generic_width`). Any other literal is a `Field` being cut down (`a_literal_outside_its_target_is_denied`), and so is what a `comptime` block or a macro call evaluates to (`comptime_blocks_cannot_launder_a_field_value`, `a_macro_result_cast_is_denied_in_run_time_and_comptime_code`). `bool as Field`, `Field as Field` and integer-to-integer casts cross no boundary and are untouched (`casts_that_do_not_cross_the_field_boundary_are_untouched`). These tests are in [`field_cast`](../compiler/noirc_frontend/src/tests/field_cast.rs). The error names the fix that fits the cast: `Field::from` where the standard library's `From` converts every value of the source (`the_denial_of_a_cast_into_field_suggests_from_where_every_value_fits` in [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs)), a typed literal for a negative literal its target holds, a declared type for a value that is a `Field` only by default (`the_denial_of_a_defaulted_value_suggests_giving_it_a_type`), and `TryFrom` or `UnsafeFrom` otherwise. Reduction and truncation are refused as an unstated meaning of `as` because reduction makes the cast non-injective and both depend on the field; they are offered under a name instead.
   - **No crate is exempt.** The standard library converts as every other crate does and writes no such cast: `the_standard_library_is_denied_the_cast_too` in `field_cast` pins the rule for its crate, and `stdlib_never_casts_between_field_and_an_integer` in [`stdlib_field_casts`](../compiler/noirc_driver/tests/stdlib_field_casts.rs) checks the library itself under every field, with either half of its gated items compiled. Where a cast lands makes no difference either: code a macro writes (`macro_output_is_judged_where_it_lands`) and code `Expr::resolve` type checks inside a standard library function (`a_cast_resolved_inside_the_stdlib_is_denied_where_it_is_spliced` in [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs)) are denied like any other.
   - **The conversions.** [`convert`](../noir_stdlib/src/convert.nr) holds three traits with three contracts. `From` is lossless and exists only where every value of the source fits, so `Field: From<u64>` and `Field: From<u128>` are excluded under Goldilocks. `TryFrom` exists for every integer type under every field and returns `None` for a value that does not fit. `UnsafeFrom` exists for every integer type under every field and wraps: into `Field` modulo p, out of `Field` to the low bits of the target read by its signedness. A signed source converts as its bit pattern, so `-1_i8` is `255` and never `p - 1`. `TryFrom` is `UnsafeFrom` and a comparison of the round trip, skipped where the target is the wider of the two and so holds every value (the `try_from_that_always_fits` program in `test_programs/compile_success_empty` compiles to its input's range check alone), so it holds no modulus of its own. Neither is in the prelude, so a program that uses one names it. `unsafe_from_reduces_and_truncates_at_the_boundaries` and `try_from_is_some_exactly_when_the_value_fits` in [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs) run both under every field. `AsPrimitive` converts between integer types only (`as_primitive_does_not_cross_the_field_boundary` in [`stdlib_field_casts`](../compiler/noirc_driver/tests/stdlib_field_casts.rs)).
   - **Lossless conversions.** `From<uN> for Field` is declared with the same `field_cast` builtin as `UnsafeFrom`, so `Field::from(x)` is the cast itself in the monomorphized program, as `x as Field` was, and a backend that tracks the range of a value keeps it through the conversion. As a call to a function holding the cast it did not: under Mavros a program that takes a `u8` into a `Field` and back grew from 60 R1CS rows to 322. The builtin converts a type of any width, so the type checker does not stop such an impl from existing for a type that can reach the modulus, where it would reduce. `stdlib_conversions_into_field_follow_the_field_width` in `stdlib_field_casts` checks under every field that these impls exist exactly for the types whose every value lies below p (`FieldConfig::fits_unsigned`); the `#[field(not(goldilocks))]` gates on `From<u64>` and `From<u128>` are what it holds in place.
   - **What a cast computes.** The cast of the monomorphized program is total. `UnsafeFrom` between `Field` and an integer is the `field_cast` builtin, declared on the trait methods themselves, and the monomorphizer replaces a call with the cast it stands for, so a program that converts holds casts and no call to a builtin (`lowers_the_field_cast_builtin_to_casts` and `wraps_the_field_cast_builtin_as_a_function_value` in the [monomorphizer's tests](../compiler/noirc_frontend/src/monomorphization/tests.rs), and `stdlib_conversions_between_field_and_integers_are_casts` in `stdlib_field_casts` for the library's own impls). A signed integer enters the field through the unsigned type of its width. A cast to `Field` is the source's own-width bit pattern modulo p. A cast to an integer keeps the low bits of the target width and reads them by the target's signedness, without any intermediate field value, so a `u64` above p survives `as u128` unchanged. The comptime interpreter's [`cast`](../compiler/noirc_frontend/src/hir/comptime/interpreter/cast.rs) module implements this on `BigInt`: `casts_into_field_reduce_at_the_corners_of_every_width` and `casts_out_of_field_keep_the_low_bits_at_the_corners_of_every_width` check it at widths on both sides of every field's own, `casts_follow_the_bit_pattern_model_at_every_width` checks it against a bit-pattern model, and `integer_casts_do_not_reduce_modulo_the_field` pins the integer-to-integer direction. These are the values Mavros computes for the same cast (`int_to_field` and `field_to_int` in its `int-semantics/src/lib.rs`). This compiler's own back end never lowers a cast that reduces, since the driver refuses every integer type that can reach the linked modulus before SSA (`ensure_integer_widths_are_lowerable` in [`noirc_driver`](../compiler/noirc_driver/src/lib.rs)).
2. **Canonical `Field` values error, never wrap.** A `Field` literal must lie in `[0, p)` of the configured field (`check_integer_literal_fits_its_type` in [`lints`](../compiler/noirc_frontend/src/elaborator/lints.rs), pinned for every configuration by `field_literals_must_be_canonical`), and converting a `BigInt` whose magnitude is not below p into a field value is refused (`FieldValue::try_from_bigint` in [`field_value`](../acvm-repo/acir_field/src/field_value.rs)). A negated literal is one literal whatever its size, so `-1` is `p - 1` and `-p` is refused by the same bound on its magnitude (`negative_field_literals_are_bounded_by_their_magnitude`). These conversions reject noncanonical magnitudes instead of reducing them.
3. **Integer literals are exact.** Integer types at every legal width are legal under every field inside a program, and the monomorphized AST carries their values exactly as `BigInt` literals, however narrow the field (`integer_literals_above_the_modulus_stay_exact`); an entry point's signature takes every width too, since its values cross as bytes (see the entry-point section). The lexer's ceiling is the field-independent `2^16384 - 1`, the largest value of the widest integer type (`test_int_too_large`); the per-type bound is applied at type-check (`literal_bounds_hold_at_every_width`), and again by the monomorphizer for a literal whose type has a generic width (`a_literal_of_a_generic_width_is_bounded_once_the_width_is_bound`). The back half of the compiler reduces these values through the field; a consumer of the monomorphized AST lowers them natively.
4. **Integer arithmetic is checked.** `+`, `-`, `*`, `/`, `%` and negation report overflow instead of wrapping, at every legal width (`attempt_to_add_with_overflow_at_comptime` in [`metaprogramming`](../compiler/noirc_frontend/src/tests/metaprogramming.rs) and `comptime_arithmetic_and_casts_work_at_wide_widths` in `width_contract`; the operator impls in [`integer`](../compiler/noirc_frontend/src/hir/comptime/integer.rs) compute on `BigInt` and refuse a result outside the width). Casts wrap and arithmetic does not; neither rule is adjusted toward the other.

# Integer widths

An integer type is a signedness and a width in bits, and the width is a number: every width from 2 through 16384, odd or even, for both signednesses (`is_legal_integer_width` in [`integer_width`](../compiler/noirc_frontend/src/shared/integer_width.rs)). The cap is the one Mavros lowers, its `MAX_SUPPORTED_INT_BITS = 1 << 14` (`compiler/src/compiler/ssa/hlssa/type_system.rs`, asserted equal to `MAX_BITS` in its `int-semantics/src/lib.rs`), so no width the front half admits is one the consumer of the monomorphized output refuses on principle; which widths its lowerings cover is its own, per-operation question. `u34` and `u<34>` name the same type; `u<N>` takes a `u32` generic and `u<2 * N>` an arithmetic expression over one, so [`Type::Integer`](../compiler/noirc_frontend/src/hir_def/types.rs) carries the width as a type of kind `u32`, like an array length, and unifies it the same way: `u<N>` binds `N` against `u34`, and a generic impl for `u<N>` covers every unsigned width. In a cast the parametric spelling needs the turbofish, `x as u::<2 * N>`, because `x as u<N>` already reads as a comparison, and the formatter keeps it (`format_cast_to_a_generic_width_keeps_the_turbofish` in [`expression`](../tooling/nargo_fmt/src/formatter/expression.rs)). `u` and `i` on their own stay ordinary identifiers; the family is recognised only when generic arguments follow, and the families sit in the same fallback position every named primitive already occupies: a program's own item of that name wins. A width the language does not have is refused where it is written (`UnsupportedIntegerWidth`), in an expression path such as `u16385::max_value()` too, where the name is looked up as a primitive type rather than resolved as a type (`a_width_the_language_does_not_have_is_refused_in_an_expression_path`), and one that becomes a number only at monomorphization is refused there; the comptime interpreter binds generic widths as well and refuses one the same way where it would create a value of that type, in a cast, a literal or `zeroed` (`a_generic_width_is_checked_at_comptime_too`). `i128` is nameable. Width 1 is refused in every spelling, `u1`, `i1`, `u<1>`, `i<1>` and a generic width bound to 1 at monomorphization, and every spelling prints the same instruction, "`u1` has been removed, use `bool` instead" (`RemovedType` for the name, `unsupported_integer_width_diagnostic` in [`errors`](../compiler/noirc_frontend/src/hir/resolution/errors.rs) for the rest, pinned by `every_spelling_of_width_1_says_use_bool_and_width_0_is_refused`). It is never an alias of `bool`: an alias would make `u<N>` at `N = 1` the same type as `bool` and put every `impl` on `bool` in coherence with the `u<N>` impls. `u0` and `i0` are integer type names of a width the language refuses (`parse_integer_type_name` reads a lone `0`), so they get the width diagnostic rather than an unresolved name. Literal suffixes stay the fixed ten.

The front half admits every legal width inside a program and the monomorphized output carries it as a number (`ast::Type::Integer(Signedness, u32)`), which is what a consumer of that output takes; an entry point takes and returns every legal width as well. The circuit backend lowers `u8` through `u128` and `i8` through `i64` (its signed comparison and truncation carry one bit more than the operand and were written for at most 64 signed bits, so `i128` is nameable but not lowerable); the set is `is_lowerable_integer_width` in [`integer_width`](../compiler/noirc_frontend/src/shared/integer_width.rs). It carries each integer in one element of the field it is built for, so of that set it lowers only the widths below the linked modulus (`FieldConfig::linked().fits_unsigned`): every one under bn254 and bls12_381, `u8` through `u32` and `i8` through `i32` under Goldilocks; `unlowerable_integer` in [`integer_width`](../compiler/noirc_frontend/src/shared/integer_width.rs) names the rule a type fails for the driver. `ensure_integer_widths_are_lowerable` in [`noirc_driver`](../compiler/noirc_driver/src/lib.rs) refuses any other width between monomorphization and circuit generation, on the circuit path only, the way `ensure_field_is_linked` refuses a field the backend was not built for, naming the rule the width fails (`UnsupportedIntegerWidth` or `IntegerExceedsLinkedField`); `check_crate` accepts every width, so a `main` that takes a `u24` passes `nargo check` and is refused by `nargo compile`, with no source location ([`entry_point_width_u24`](../test_programs/compile_failure/entry_point_width_u24/src/main.nr)). The SSA generator still refuses, rather than reduces, an exact literal whose magnitude is at or above the linked modulus (`RuntimeError::IntegerExceedsField`), for consumers that lower a monomorphized program without the driver. [`width_contract`](../compiler/noirc_frontend/src/tests/width_contract.rs) pins resolution in every generic position, the literal bounds, comptime arithmetic and casts, and the monomorphizer's checks under every field configuration; the driver's [`integer_widths`](../compiler/noirc_driver/tests/integer_widths.rs) pins the boundary.

# Field gating

`#[field(<name or modulus>)]` keeps an item for one field; `#[field(not(<name or modulus>))]` excludes that field. Names are case-insensitive (`bn254`, `bls12_381`, `goldilocks`); moduli may be decimal or hexadecimal. Unknown names produce a warning. Numeric moduli remain valid even when unsupported. Multiple field attributes must all match.

The gate applies to functions, globals, structs, enums, traits, type aliases, inherent impls and their methods, whole trait impls, and modules. It does not apply to `use` declarations, so a module that must name a gated-out item reaches it through a gated type alias. It also applies to comptime-generated structs, enums, functions and impls. Items are dropped before name resolution and type checking, so same-named definitions can target different fields. A gated external module is skipped before looking up its file; inline module bodies must still parse. The formatter keeps the attribute as written, `not(..)` included. A gated item is field-specific even under the field it names, so it cannot cross an entry point (see the entry-point section).

A gate names a field, not a property of one. Where the standard library keeps two definitions of an item, the `not(bn254)` half is written for any field and the `bn254` half for the one whose modulus holds a `u128`, and so every integer type the backend lowers, and decomposes into two limbs. `bls12_381` holds a `u128` too but takes the generic half of the wrapping and hashing impls, which is correct and costs more constraints than the bn254 half; `Field::lt`'s bn254 half rests on bn254's own limb constants, so no other field could share it. A predicate on the modulus width would let a second wide field take the cheaper halves; it is not written because no build targets one, and the attribute grammar would grow for a cost nobody pays. The standard library has no function that reports which field it is compiled for: code that differs by field is a gated pair, which the collector sees, where a question asked of the modulus inside one definition would hide a field-dependent branch from it (`the_standard_library_does_not_name_its_field` in [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs)).

Inherent and trait impls directly naming an excluded local struct or enum are skipped unless a retained definition or import supplies that name. Qualified paths and impls in other modules require their own gates. Collection lives in [`dc_mod`](../compiler/noirc_frontend/src/hir/def_collector/dc_mod.rs); [`field_attribute`](../compiler/noirc_frontend/src/tests/field_attribute.rs) covers selection, name collisions, and generated items.

`--generic-builtins` (`CompileOptions::generic_builtins`, hidden on nargo, off by default) is a benchmark mode for bn254 builds, not a language feature: no attribute or syntax changes, and one binary produces both variants. Under it the gates that name bn254 read the other way round where a module keeps both halves of an item: a `#[field(not(bn254))]` item is kept, and a `#[field(bn254)]` item is dropped exactly when the module also has its *twin*, an item of the same kind and name gated `not(bn254)` that its other gates admit (`TwinKey` and `generic_twins` in `dc_mod`; an inherent impl is named by its object type as written, a method by that and its name, a trait impl by its trait and object type as written). Pairing is per module, so the standard library's twins are the ones the mode flips: `Field::lt`, `Hash` for `u64`, `u128` and `i64`, and the wrapping arithmetic for `u32`, `u64` and `u128` (all but `WrappingAdd for u128`, which has one definition), together with their `not(bn254)` helpers; an item written for one field with no twin, such as pedersen, Poseidon2, the embedded curve, `field::bn254` or the `bn254` module of the wrapping arithmetic, is kept, so every program that compiles without the mode compiles with it. Gates naming other fields or moduli are evaluated as always, and items generated at compile time have no twins. Under another field the option changes nothing (`FrontendOptions::field_gates`): the standard library keeps no halves written for Goldilocks, and its `not(goldilocks)` gates mark items the field's range excludes, `From<u64>` and `From<u128>` for `Field`, which a benchmark must not bring back. Hashes of the wide integers change under the mode, which is why it is a benchmark option: it exists so the field-generic definitions can be measured against the bn254 ones on one backend before deciding, per builtin, which to keep. The dropped bn254 halves that go through `Field` leave their functions in `ops::arith::bn254` unused, a warning `check_crate` never reports since it keeps only the root crate's warnings. `generic_builtins_*` in `field_attribute` pins the pairing for every kind of item, the per-module rule and the twins other gates exclude; in [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs), `bn254_takes_the_generic_halves_under_generic_builtins` runs the Goldilocks checks of the generic halves under bn254 with the option and shows the limb hash failing without it, `the_compile_option_reaches_the_frontend` takes the option through `CompileOptions`, and `generic_builtins_leave_the_stdlib_compiling_under_every_field` pins the other fields. The `NodeInterner` holds the field and the option together as `FieldGates`, seeded once per compilation.

# Standard library conversions into `Field`

`From<u64>` and `From<u128>` in [`convert`](../noir_stdlib/src/convert.nr) are excluded under Goldilocks because their full ranges exceed its modulus. Both fit BN254 and BLS12-381. `TryFrom` and `UnsafeFrom` take every integer type under every field, and `AsPrimitive` converts between integer types only. [`stdlib_field_casts`](../compiler/noirc_driver/tests/stdlib_field_casts.rs) checks these conversion boundaries.

# Integer code first

Standard library code on integers is integer code under every field. A definition written for bn254 is kept beside it only where it takes strictly fewer ACIR opcodes on bn254, measured with `nargo info` on a program that is one call (`--generic-builtins` gives the other half's count from the same binary), and it goes through `Field` only where that is what makes it cheaper.

Wrapping arithmetic in [`arith`](../noir_stdlib/src/ops/arith.nr) follows from that. An operation on `u8` or `u16` is done in the type twice as wide and cut back, with no gate, since every field holds a `u32`. `u32` and `u64` do the same under bn254, which holds the wider type; elsewhere the wider type can reach the modulus, which the linked backend refuses. There `u32` goes through `Field` (the `through_field` module of `arith`): the other fields' moduli hold the sum and the product of two `u32`, and under a 64-bit field that costs a backend less than integer code that stays inside the type. `u64` stays inside its type, where addition and subtraction avoid overflow through a comparison and multiplication is done in `u128`. `u128` has no wider type the backend lowers: addition is the comparison form under every field, and subtraction and multiplication keep a bn254 half beside the integer one, whose multiplication combines 64-bit limbs and divides by a constant (`wrapping_u128_multiplication_divides_by_a_constant`: a divisor handed in as an argument is a variable to a backend that does not specialise the callee). The halves that go through `Field` are `WrappingSub for u128`, `WrappingMul for u64` and `WrappingMul for u128`, in the `bn254` module of `arith`, which is the only part of the file that names the conversions. Measured ACIR opcodes on bn254, the kept definition first and its integer twin after it where there is one:

| | `u8` | `u16` | `u32` | `u64` | `u128` |
|---|---|---|---|---|---|
| `wrapping_add` | 7 | 7 | 7 / 13 | 7 / 13 | 15 |
| `wrapping_sub` | 9 | 9 | 9 / 15 | 9 / 15 | 16 / 17 |
| `wrapping_mul` | 7 | 7 | 7 / 49 | 14 / 16 | 46 / 68 |

`integer_wrapping_arithmetic_names_field_only_where_it_is_cheaper` in [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs) pins which operations name `Field` in the monomorphized program under each field, and `goldilocks_stdlib_fallbacks_preserve_values` checks the integer definitions at the corners of every width.

`Hash` for `u64`, `u128` and `i64` in [`hash`](../noir_stdlib/src/hash/mod.nr) writes the value as one field element under bn254 (5 opcodes) and as 32-bit limbs elsewhere (14, 34 and 14 on bn254), since a `Hasher` takes field elements.

`Ordering` in [`cmp`](../noir_stdlib/src/cmp.nr) holds its three states as a `u8`, so comparing integers through `Ord` names no `Field` (`ordering_holds_no_field` in `stdlib_elaboration`). The compiler reads that value where it lowers `<`, `<=`, `>` and `>=` on a type with an `Ord` impl, in the monomorphizer and in the comptime interpreter's `evaluate_ordering`, and both compare it as a `u8`. A program that compares through `Ord` takes the same number of ACIR and Brillig opcodes on bn254 as it did when the value was a `Field`.

`Field::lt` uses the BN254 implementation under that field and canonical byte comparison elsewhere, sized to the configured modulus. The embedded curve and Poseidon2 module are BN254-only. The derive registry uses a non-cryptographic multiply-add hasher for its comptime map.

# The width-generic standard library

`Add`, `Sub`, `Mul`, `Div`, `Rem`, `Neg`, bitwise traits, `Eq`, `Ord`, and `Default` have generic implementations for integer families. Inherent `max_value`, `min_value`, and `bits` derive their results from the width. Primitive operators already support these widths; the trait impls make them usable in generic functions.

`Hash`, `From`, `AsPrimitive`, and wrapping arithmetic retain their explicit width lists. [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs) executes numeric trait and limit checks under each configured field, verifies Goldilocks arithmetic, hash limbs and comparison fallbacks, and checks cryptographic API gating.

# Entry-point values: bytes, the same on every field

`main` and the entry functions of a contract take and return values that cross as bytes, the same on every field, so their types carry no field: integers of every legal width, `bool`, `str<N>`, and fixed arrays, tuples and structs of them. The rule is `program_validity` under `ProgramBoundary::EntryPoint` in [`validity`](../compiler/noirc_frontend/src/hir_def/types/validity.rs), reported as `InvalidTypeForEntryPoint`, and it refuses, wherever the signature holds them (through an array, tuple, struct, alias or generic argument, and in the return):

- `Field` (`InvalidType::Field`), whose values depend on the field;
- a type that is still unbound (`Unbound`), such as an `impl Trait` parameter, which has no size before the program runs;
- a struct, enum or alias that is field-specific, marked `#[field(..)]` itself or through an enclosing module (`FieldGated`, whose diagnostic points at the attribute). The gate is recorded on the item when it is collected (`field_gate` in [`dc_mod`](../compiler/noirc_frontend/src/hir/def_collector/dc_mod.rs)), and an entry point that carries the attribute itself, or sits in a module or contract that does, is refused by the `field_attribute_on_entry_point` lint (`FieldAttributeOnEntryPoint`).

The rule is decided on the type, before any value exists, so an accepted signature has the same byte layout under every field. The body may still depend on field-specific operations or conversions. Test and fuzz functions, the return of a `#[no_predicates]` function and `#[abi(tag)]` globals cross no such boundary and are checked under `ProgramBoundary::Harness`: any sized type, `Field` included. As upstream, every boundary refuses a zero-length array or string among the parameters and accepts one in the return, where it takes no bytes, and a struct with no fields crosses anywhere; `()` still means "no return". An entry point names each parameter once, `_` included (`DuplicateNameForEntryPoint`): a parameter's name is the key of its input, and `check_abi` refuses an ABI that repeats one, so a signature the frontend accepts always has a byte encoding (`rejects_repeated_wildcard_names_in_entry_point_params` in [`functions`](../compiler/noirc_frontend/src/tests/functions.rs)). An `#[export]` function is outside the rule as it is outside `program_validity` altogether: `NoirFunction::is_entry_point` names only `main` at a crate root and a contract's entry points, so a `main` at the root of a dependency crate follows the rule too. `abi_gen` builds an entry point's ABI strictly, as an internal error on an unbound type, while error payloads and contract output structs keep the lenient default for an unpinned literal ([`abi_gen`](../compiler/noirc_driver/src/abi_gen.rs)). The monomorphizer caps an entry point's inputs at fewer than 2^32 bytes together, and its return at fewer than 2^32 bytes on its own (`MAX_INPUT_BYTES` in [`ast`](../compiler/noirc_frontend/src/monomorphization/ast.rs), `InputSizeExceeded` and `ReturnSizeExceeded`), after the per-parameter `MAX_ELEMENTS` limit. [`field_contract`](../compiler/noirc_frontend/src/tests/field_contract.rs) pins the rule under every field (`every_legal_integer_width_crosses_main`, `field_is_refused_at_main_wherever_the_type_holds_it`, `the_entry_point_rule_leaves_other_functions_alone`, `contract_functions_follow_the_entry_point_rule`, `abi_tag_globals_keep_field`, `the_entry_point_diagnostic_explains_the_field_rule`), [`entry_point_size`](../compiler/noirc_frontend/src/tests/entry_point_size.rs) pins the byte cap, and the [`compile_failure`](../test_programs/compile_failure) programs `field_in_main`, `field_in_main_struct`, `field_gated_type` and `databus_unsupported` pin nargo's output. The data bus is refused for the same reason ([`databus`](databus.md)).

Every type an entry point takes is range-checked as it enters the circuit, one opcode per scalar, so a program with inputs never compiles to an empty circuit. The `compile_success_empty` tests therefore expect exactly those range checks, each at its input's own width, and no other opcode (`compile_success_empty` in [`execute`](../tooling/nargo_cli/tests/execute.rs)).

`noirc_abi::bytes` ([`bytes`](../tooling/noirc_abi/src/bytes/mod.rs)) is the entry point's codec. It reads TOML or JSON inputs into one little-endian byte blob, the same on every field, and back: an integer of width w is its w-bit two's complement pattern in `ceil(w / 8)` bytes with the padding bits zero, a `bool` is one byte `0` or `1`, a `str<N>` is N raw bytes, and arrays, tuples and structs follow in declaration order with no alignment and no length prefix, so an empty value takes no bytes (it counts as one byte against the 2^32 cap, so that an empty blob cannot declare unboundedly many values); the return is a blob of its own. Decoding refuses set padding bits, a `bool` byte other than `0` or `1`, and any length but the exact one. The parser reads inputs as Noir's input parser does, except that shapes are exact: a missing key is an error, while a key that names no parameter or field is ignored and a key repeated in JSON takes its last value, a quoted number is read as Noir's input parser reads it (an optional `-`, `0x` and `+`, then digits with `_` separators, `"-0"` being 0 for every type), a `bool` is `true`, `false`, `0` or `1` as in Noir's input parser, and `check_abi` refuses an ABI that names `Field` or a width outside 2..=16384. `byte_vectors` in [`conformance`](../tooling/noirc_abi/src/conformance.rs) supplies the shared golden, accept and refuse cases, and `the_codec_accepts_and_refuses_exactly_the_byte_vectors` pins the codec to them.

The field codec below stays for nargo's circuit path, which carries each scalar in one field element (`AbiType::field_count`) and so takes only the integer widths the driver lowers. It has three layers, so that a consumer other than the circuit backend chooses the field at run time. `Format::parse` in the [input parser](../tooling/noirc_abi/src/input_parser/mod.rs) reads TOML or JSON inputs under a `FieldConfig` its caller passes; `encode_scalar` and `decode_scalar` in [`scalar`](../tooling/noirc_abi/src/scalar.rs) convert between a scalar and its element under a `FieldConfig`, as the canonical integer in `[0, p)`; `Abi::encode` and `Abi::decode` build and read the backend's `WitnessMap<FieldElement>` and are linked-field by their type, so a field mismatch cannot be expressed there. A parsed value is held in `InputValue::Field`, whose linked element is an exact container for every field whose modulus is at most the linked one; a field with a larger modulus is refused before any value is read (`FieldNotCarried`), so one bn254 build parses bn254 and Goldilocks inputs, and bls12_381 inputs need a bls12_381 build (`a_field_the_linked_element_cannot_hold_is_refused`).

The value rule, applied by `scalar_to_field` in the input parser and by `decode_scalar`: an integer is accepted iff it lies in the range of its type **and** its unsigned fixed-width bit pattern is below p; a `bool` is `0` or `1`; a `Field` is any value below p, a negative native spelling denoting the negation of its magnitude in the selected field while a quoted spelling must be non-negative. Nothing is reduced at this boundary, so accepted signed values never collide modulo p, and a backend that reduces an integer return modulo p cannot serve as an oracle for one whose pattern reaches p (the driver's width gate leaves a program it compiles no such return). The driver's width gate keeps the inputs of a program nargo compiles inside this domain; the value rule is what an ABI written by hand, or an `InputValue` built without compiling, meets: under Goldilocks a `u64` accepts exactly the values below p and an `i64` exactly `[-2^63, -2^32] ∪ [0, 2^63 - 1]`, because `-2^32` encodes as `p - 1` and `-1` as `2^64 - 1 ≥ p`. Refusals name the selected field and its modulus. `Format::parse` owns the check for both formats and for quoted and native spellings alike, because consumers other than `nargo` stop there and never reach `Abi::encode`; `find_type_mismatch` repeats the type-range half for callers that build an `InputValue` directly. The boundary vectors below pin the domain and `field_values_are_accepted_iff_below_the_selected_modulus` in the input parser pins the refusal's wording, under every field the build carries.

`boundary_vectors` in [`conformance`](../tooling/noirc_abi/src/conformance.rs) supplies shared accept and reject cases for the field parser and ast-interpreter's `Prover.toml` bridge: `p - 1`, `p` and `p + 1`, the 64-bit values on either side of the Goldilocks modulus, the widest width the parser carries (one bit short of the modulus, which a hand-written ABI can still name) and one bit wider, and spellings each scalar type refuses. `the_parser_accepts_and_refuses_exactly_the_boundary_vectors` pins the parser to them.

`FieldConfig::num_bytes` rounds a modulus up to whole 64-bit limbs and sets the padding for `FieldValue::to_hex` and ABI tags. Signed `InputValue` serialization uses the linked element's width, even when its value was parsed under another field; JSON serialization of unsigned and `Field` values trims leading zeroes. For the linked field, `num_bytes` agrees with the element's hex width (`every_boundary_value_agrees_with_the_linked_field_element`).

Integers wider than the field cross an entry point in the byte encoding, which carries its own version (`BYTE_ENCODING_VERSION`); the field codec carries none, and there is no "elements per integer" property anywhere in the compiler.

# Run-time field configuration

[`FieldId`](../acvm-repo/acir_field/src/field_config.rs) names a supported field: `bn254`, `goldilocks`, and `bls12_381`. Its discriminant is the wire code, decoded only through the checked `from_code`, and it has no `Default`, so a field is always named deliberately. `FieldConfig` holds an id and answers every question the front half asks about its field (`modulus`, `num_bits`, `fits_unsigned`, whether a `width`-bit unsigned type is carried in one element, and `matches_field_attribute`) from rows written out in that file, deliberately not from the `FieldElement` alias the crate is built with, so a bn254 build answers Goldilocks queries. Each row-dependent accessor is an exhaustive `match` with no fallthrough arm, so a new field is a compile error until it has a row (`every_row_states_its_modulus_and_width`), and `the_linked_row_agrees_with_the_linked_field_element` pins the row of the built field to the linked element under whichever field the crate is built with. Two rules keep the front half field-generic: a layer only asks the configuration (modulus, width, whether a width fits) and never names a field or compares against a width literal; and a layer never uses `FieldElement` as the carrier for a value that is not semantically a `Field`.

The configuration is seeded once per compilation. It travels from `--field` on [`CompileOptions`](../compiler/noirc_driver/src/lib.rs) through `FrontendOptions` into the [`NodeInterner`](../compiler/noirc_frontend/src/node_interner/mod.rs), the one object every pass from definition collection to monomorphization holds, at the first elaboration entry point (`collect_defs_and_elaborate` and `Elaborator::new`); a query before that, or a second seed with a different field, is an internal error. Definition collection, the literal lint, the comptime and monomorphization `modulus_*` builtins and the comptime cast widths all read `interner.field()`, and frontend tests compile and execute comptime code under any row in one build (`GetProgramOptions::for_field`).

The monomorphizer's `into_output` returns a `MonomorphizationOutput`: the program and the `FieldId` it was compiled under. The label travels beside the program, never inside it, and consumers must check it before lowering (`output_is_labeled_with_the_configured_field`).

# Comptime values carry their field

A comptime `Field` value is a [`FieldValue`](../acvm-repo/acir_field/src/field_value.rs): a canonical representative in `[0, p)` together with its `FieldId`. `Integer::Field` uses this carrier for interpreter evaluation and type-level arithmetic. Operations reduce modulo the configured field; mixing fields is an internal error. Native integer variants keep their checked arithmetic.

Tests compare arithmetic, formatting and signed conversions against the linked `FieldElement` at random and boundary values. BN254 hashing also stays compatible because compile-time reflection exposes it. Signed conversions choose by bit length; `Display` chooses by decimal length. The linked-element helpers in [`integer`](../compiler/noirc_frontend/src/hir/comptime/integer.rs) remain for SSA lowering and the fuzzer. `FieldValue::from_linked_element` converts values coming from linked carriers such as the ABI parser.

# Builtin capabilities

`FieldConfig::embedded_curve` and `has_poseidon2_permutation` control the comptime crypto builtins. BN254 supports both; other fields return `Unimplemented`. The solvers use explicit bn254 elements, independent of the compiler's linked field. `poseidon2_config_state_size` still returns bn254's width; fencing this stdlib dependency remains future work. Compile-time hashes are reduced into the configured field and need not agree across fields.

The ECDSA foreigns, `ecdsa_secp256k1` and `ecdsa_secp256r1`, are bytes in and a `bool` out and carry no field at any plane: the comptime interpreter, the ACVM and the Brillig VM dispatch them to the `k256`/`p256` solvers without a field element, so they run under every configured field. On Mavros they are rewritten into vendored Noir over 120-bit limbs, which needs a field of roughly 247 bits or more, so at run time they are bn254-only there; a Goldilocks ECDSA is a prime-field library on native wide integers, not a builtin, a flag or a `FieldConfig` member, since `#[field]` gating and a width `static_assert` already select a per-field implementation inside one crate. `keccakf1600` has no Mavros replacement under any field.

# The backend boundary

`ensure_field_is_linked` in [`noirc_driver`](../compiler/noirc_driver/src/lib.rs) rejects unsupported fields before circuit compilation, including cached artifacts. The same guard protects `nargo execute --force-comptime`, `nargo interpret` and the SSA-impact example, which read their inputs in, and evaluate with, the linked field. `check_crate` accepts any configured field, the standard library included.

ABI-tagged globals preserve canonical `Field` values and native integer magnitudes. Hex output is padded to the configured element width; wider integers retain their full magnitude, and signed integers carry their sign separately (`abi_tag_integers_preserve_sign_width_and_magnitude`).

The `bn254`, `bls12_381` and `goldilocks` features of [`acir_field`](../acvm-repo/acir_field/src/lib.rs) select the built field and are mutually exclusive (`assert_unique_feature!`), so enabling two is a compile error rather than a silent pick; `FieldId::linked` is the one place the front half reads them. Every crate that reaches the field through the `FieldElement` alias, including [`noirc_abi`](../tooling/noirc_abi/Cargo.toml), forwards a `goldilocks` feature to it. Field element conversions are width-agnostic: `to_i128` reads the shorter of an element's two spellings, on the 8-byte Goldilocks representation as on bn254's 32 bytes (`test_to_i128_roundtrip` and its `goldilocks` twin in [`field_element`](../acvm-repo/acir_field/src/field_element.rs)).

`nargo_cli` and the wasm crates hard-enable `bn254`, so the Goldilocks build is exercised by [its own workflow](../.github/workflows/goldilocks.yml): it builds `noirc_driver` with the feature and runs what only that build can check, the field crate's arithmetic, the configuration row and the run-time carrier against the linked element, the ABI crate whose parsed values and witnesses live in the linked element, the driver's boundary rule and the programs it compiles under the linked field, and the SSA probes in [`small_field_validation`](../compiler/noirc_evaluator/src/ssa/interpreter/small_field_validation.rs). The frontend field-contract tests select every field in the default build; other frontend tests run with the linked field. A change to feature-gated code is covered only if a test runs there; the default build proves nothing about it. [The fork-residual workflow](../.github/workflows/fork-residual.yml) compares the fork's diff against the upstream release named in `.github/fork-base.txt` with the committed `.github/fork-residual.txt`, so a file enters or leaves the fork's residual only together with the manifest.

# Checking the two fields against each other

The monomorphized AST is the surface compared across fields: integer, boolean and structural results must agree exactly and only `Field`-typed values may differ; a panic or internal error under either field never passes. The [ast-interpreter](https://github.com/worldfnd/ast-interpreter) executes the AST under both fields, in one build of a pinned compiler revision, since the compiler, the input parser and its own values all take the field at run time, and records the comparison per program in its committed `STATUS.md`.

# Intended direction

The SSA interpreter's numeric values follow the configured field, which lets `nargo interpret` and `nargo execute --force-comptime` run under any field; a second arithmetic backend makes the back half itself field-generic and width-generic, at which point the driver's width gate has nothing left to refuse. The ast-interpreter reads its inputs through `noirc_abi::bytes` and runs the test programs under both fields.
