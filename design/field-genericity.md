# Field genericity

Field metadata, source checks, and monomorphization use a [`FieldConfig`](../acvm-repo/acir_field/src/field_config.rs) chosen once per compilation (`--field`, default: the field the compiler is built with). The `goldilocks` feature of [`noirc_driver`](../compiler/noirc_driver/Cargo.toml) selects the field the compiler is *built* with, Goldilocks (p = 2^64 − 2^32 + 1) or bn254 by default; that field is the one the back half lowers into, and the front half runs under any configured field in the same binary. Under bn254 every backend-supported integer fits in one field element, so field arithmetic can carry integers without loss; under Goldilocks a `u64` can exceed p, so anything that carries an integer through the field silently corrupts it. The rules below say where integers must be carried exactly, where a value is reduced, and where an out-of-field value is an error. They hold under every supported field, and the tests that pin them run under every field configuration in one build.

# The value rules

1. **Casts.** `x as Field` is the identity on the value and is defined only for source types whose every value lies below p: `bool`, `Field`, and an unsigned integer type narrower than the field (`FieldConfig::fits_unsigned`). An unsigned type that can hold a value at or above p (`u64` and `u128` under Goldilocks) is refused at type check (`IntegerTypeExceedsField` in [`types`](../compiler/noirc_frontend/src/elaborator/types.rs)), whatever value it holds at run time, so whether a program compiles depends on the field. The escape hatch is an explicit narrowing cast, `(x as u32) as Field`, which keeps one uniform meaning for `as Field` under every field. Reduction modulo p is rejected because it makes the cast non-injective (`x as Field == y as Field` for `x != y`), and a run-time range check is rejected because it costs a constraint on every non-constant cast. Casting a signed integer to `Field` directly is a type error (`UnsupportedFieldCast`), so a negative value reaches `Field` only through its unsigned reinterpretation: `(-1i8 as u8) as Field == 255`, never `p - 1`. An integer-to-integer cast keeps the low bits of the target width and reads them by the target's signedness, without any intermediate field value, so a `u64` above p survives `as u128` unchanged. The comptime interpreter's [`cast`](../compiler/noirc_frontend/src/hir/comptime/interpreter/cast.rs) module implements this on `BigInt` and refuses, rather than reduces, a pattern at or above p (`field_casts_are_exact_or_refused`); `casts_follow_the_bit_pattern_model_at_every_width` checks it against a bit-pattern model and `integer_casts_do_not_reduce_modulo_the_field` pins the integer-to-integer direction. The type checker applies the rule where the cast is written, which is too early when the source is a type variable that inference binds later, as in a closure `|v| v as Field` passed to a generic function; the monomorphizer therefore checks every cast to `Field` again once its source type is concrete (`check_cast_to_field` in [`monomorphization`](../compiler/noirc_frontend/src/monomorphization/mod.rs), reported as `InvalidFieldCast` with the type checker's own diagnostic). In [`field_contract`](../compiler/noirc_frontend/src/tests/field_contract.rs), `casts_to_field_are_refused_when_the_type_can_exceed_the_modulus`, `comptime_casts_to_field_follow_the_same_rule`, `casts_to_field_through_an_inferred_type_follow_the_same_rule`, `signed_casts_to_field_through_an_inferred_type_are_refused`, `narrowing_before_a_field_cast_is_accepted_under_every_field` and `comptime_casts_wrap_to_the_target_width` pin the rule through the language, under every configuration where the rule is a type error including comptime evaluation. The rule holds at every legal width: `u66 as Field` is accepted under bn254 and refused under Goldilocks, and a cast from `u<N>` is checked by the monomorphizer once `N` is bound (`casts_to_field_follow_the_field_rule_at_every_width` in [`width_contract`](../compiler/noirc_frontend/src/tests/width_contract.rs)).
2. **Canonical `Field` values error, never wrap.** A `Field` literal must lie in `[0, p)` of the configured field (`check_integer_literal_fits_its_type` in [`lints`](../compiler/noirc_frontend/src/elaborator/lints.rs), pinned for every configuration by `field_literals_must_be_canonical`), and converting a `BigInt` whose magnitude is not below p into a field value is refused (`FieldValue::try_from_bigint` in [`field_value`](../acvm-repo/acir_field/src/field_value.rs)). A negated literal is one literal whatever its size, so `-1` is `p - 1` and `-p` is refused by the same bound on its magnitude (`negative_field_literals_are_bounded_by_their_magnitude`). These conversions reject noncanonical magnitudes instead of reducing them.
3. **Integer literals are exact.** Integer types at every legal width are legal under every field inside a program, and the monomorphized AST carries their values exactly as `BigInt` literals, however narrow the field (`integer_literals_above_the_modulus_stay_exact`); only an entry point's signature is bounded by the field (see the entry-point section). The lexer's ceiling is the field-independent `2^16384 - 1`, the largest value of the widest integer type (`test_int_too_large`); the per-type bound is applied at type-check (`literal_bounds_hold_at_every_width`), and again by the monomorphizer for a literal whose type has a generic width (`a_literal_of_a_generic_width_is_bounded_once_the_width_is_bound`). The back half of the compiler reduces these values through the field; a consumer of the monomorphized AST lowers them natively.
4. **Integer arithmetic is checked.** `+`, `-`, `*`, `/`, `%` and negation report overflow instead of wrapping, at every legal width (`attempt_to_add_with_overflow_at_comptime` in [`metaprogramming`](../compiler/noirc_frontend/src/tests/metaprogramming.rs) and `comptime_arithmetic_and_casts_work_at_wide_widths` in `width_contract`; the operator impls in [`integer`](../compiler/noirc_frontend/src/hir/comptime/integer.rs) compute on `BigInt` and refuse a result outside the width). Casts wrap and arithmetic does not; neither rule is adjusted toward the other.

# Integer widths

An integer type is a signedness and a width in bits, and the width is a number: every width from 2 through 16384, odd or even, for both signednesses (`is_legal_integer_width` in [`integer_width`](../compiler/noirc_frontend/src/shared/integer_width.rs)). The cap is the one Mavros lowers, its `MAX_SUPPORTED_INT_BITS = 1 << 14` (`compiler/src/compiler/ssa/hlssa/type_system.rs`, asserted equal to `MAX_BITS` in its `int-semantics/src/lib.rs`), so no width the front half admits is one the consumer of the monomorphized output refuses on principle; which widths its lowerings cover is its own, per-operation question. `u34` and `u<34>` name the same type; `u<N>` takes a `u32` generic and `u<2 * N>` an arithmetic expression over one, so [`Type::Integer`](../compiler/noirc_frontend/src/hir_def/types.rs) carries the width as a type of kind `u32`, like an array length, and unifies it the same way: `u<N>` binds `N` against `u34`, and a generic impl for `u<N>` covers every unsigned width. In a cast the parametric spelling needs the turbofish, `x as u::<2 * N>`, because `x as u<N>` already reads as a comparison. `u` and `i` on their own stay ordinary identifiers; the family is recognised only when generic arguments follow, and the families sit in the same fallback position every named primitive already occupies: a program's own item of that name wins. A width the language does not have is refused where it is written (`UnsupportedIntegerWidth`), in an expression path such as `u16385::max_value()` too, where the name is looked up as a primitive type rather than resolved as a type (`a_width_the_language_does_not_have_is_refused_in_an_expression_path`), and one that becomes a number only at monomorphization is refused there. `i128` is nameable. Width 1 is refused in every spelling, `u1`, `i1`, `u<1>`, `i<1>` and a generic width bound to 1 at monomorphization, and every spelling prints the same instruction, "`u1` has been removed, use `bool` instead" (`RemovedType` for the name, `unsupported_integer_width_diagnostic` in [`errors`](../compiler/noirc_frontend/src/hir/resolution/errors.rs) for the rest, pinned by `every_spelling_of_width_1_says_use_bool_and_width_0_is_refused`). It is never an alias of `bool`: an alias would make `u<N>` at `N = 1` the same type as `bool` and put every `impl` on `bool` in coherence with the `u<N>` impls. `u0` and `i0` are integer type names of a width the language refuses (`parse_integer_type_name` reads a lone `0`), so they get the width diagnostic rather than an unresolved name. Literal suffixes stay the fixed ten.

The front half admits every legal width inside a program and the monomorphized output carries it as a number (`ast::Type::Integer(Signedness, u32)`), which is what a consumer of that output takes; the integers an entry point takes or returns are the lowerable types, bounded by the field, below. The circuit backend lowers `u8` through `u128` and `i8` through `i64` (its signed comparison and truncation carry one bit more than the operand and were written for at most 64 signed bits, so `i128` is nameable but not lowerable); the set is `is_lowerable_integer_width` in [`integer_width`](../compiler/noirc_frontend/src/shared/integer_width.rs), and `ensure_integer_widths_are_lowerable` in [`noirc_driver`](../compiler/noirc_driver/src/lib.rs) refuses any other width between monomorphization and circuit generation, on the circuit path only, the way `ensure_field_is_linked` refuses a field the backend was not built for; `check_crate` accepts every width inside a program. [`width_contract`](../compiler/noirc_frontend/src/tests/width_contract.rs) pins resolution in every generic position, the literal bounds, comptime arithmetic and casts, and the monomorphizer's checks under every field configuration; the driver's [`integer_widths`](../compiler/noirc_driver/tests/integer_widths.rs) pins the boundary.

# Field gating

`#[field(<name or modulus>)]` keeps an item for one field; `#[field(not(<name or modulus>))]` excludes that field. Names are case-insensitive (`bn254`, `bls12_381`, `goldilocks`); moduli may be decimal or hexadecimal. Unknown names produce a warning. Numeric moduli remain valid even when unsupported. Multiple field attributes must all match.

The gate applies to functions, globals, structs, enums, traits, type aliases, inherent impls and their methods, whole trait impls, and modules. It does not apply to `use` declarations, so a module that must name a gated-out item reaches it through a gated type alias. It also applies to comptime-generated structs, enums, functions and impls. Items are dropped before name resolution and type checking, so same-named definitions can target different fields. A gated external module is skipped before looking up its file; inline module bodies must still parse. The formatter keeps the attribute as written, `not(..)` included.

A gate names a field, not a property of one. Where the standard library keeps two definitions of an item, the `not(bn254)` half is written for any field and the `bn254` half for the one whose modulus holds a `u128` and decomposes into two limbs. `bls12_381` holds a `u128` too but takes the generic half of the wrapping and hashing impls, which is correct and costs a comparison the field path does not need; `Field::lt`'s bn254 half rests on bn254's own limb constants, so no other field could share it. A predicate on the modulus width would let a second wide field take the cheaper halves; it is not written because no build targets one, and the attribute grammar would grow for a cost nobody pays.

Inherent and trait impls directly naming an excluded local struct or enum are skipped unless a retained definition or import supplies that name. Qualified paths and impls in other modules require their own gates. Collection lives in [`dc_mod`](../compiler/noirc_frontend/src/hir/def_collector/dc_mod.rs); [`field_attribute`](../compiler/noirc_frontend/src/tests/field_attribute.rs) covers selection, name collisions, and generated items.

`--generic-builtins` (`CompileOptions::generic_builtins`, hidden on nargo, off by default) is a benchmark mode for bn254 builds, not a language feature: no attribute or syntax changes, and one binary produces both variants. Under it the gates that name bn254 read the other way round where a module keeps both halves of an item: a `#[field(not(bn254))]` item is kept, and a `#[field(bn254)]` item is dropped exactly when the module also has its *twin*, an item of the same kind and name gated `not(bn254)` that its other gates admit (`TwinKey` and `generic_twins` in `dc_mod`; an inherent impl is named by its object type as written, a method by that and its name, a trait impl by its trait and object type as written). Pairing is per module, so the standard library's twins are the ones the mode flips: `Field::lt`, `Hash` for `u64`, `u128` and `i64`, and the wrapping arithmetic for `u64` and `u128`, together with their `not(bn254)` helpers; an item written for one field with no twin, such as pedersen, Poseidon2, the embedded curve, `field::bn254` or the bn254 half's private helpers, is kept, so every program that compiles without the mode compiles with it. Gates naming other fields or moduli are evaluated as always, and items generated at compile time have no twins. Under another field the option changes nothing (`FrontendOptions::field_gates`): the standard library keeps no halves written for Goldilocks, and its `not(goldilocks)` gates mark items the field's range excludes, `From<u64>` and `From<u128>` for `Field`, which a benchmark must not bring back. Hashes of the wide integers change under the mode, which is why it is a benchmark option: it exists so the field-generic definitions can be measured against the bn254 ones on one backend before deciding, per builtin, which to keep. The dropped bn254 half of `WrappingMul for u128` leaves its private helper unused, a warning `check_crate` never reports since it keeps only the root crate's warnings. `generic_builtins_*` in `field_attribute` pins the pairing for every kind of item, the per-module rule and the twins other gates exclude; in [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs), `bn254_takes_the_generic_halves_under_generic_builtins` runs the Goldilocks checks of the generic halves under bn254 with the option and shows the limb hash failing without it, `the_compile_option_reaches_the_frontend` takes the option through `CompileOptions`, and `generic_builtins_leave_the_stdlib_compiling_under_every_field` pins the other fields. The `NodeInterner` holds the field and the option together as `FieldGates`, seeded once per compilation.

# Standard library conversions into `Field`

`From<u64>` and `From<u128>` in [`convert`](../noir_stdlib/src/convert.nr) are excluded under Goldilocks because their full ranges exceed its modulus. Both fit BN254 and BLS12-381. Generated `AsPrimitive<Field>` impls use the configured width and skip types with `bits >= modulus_num_bits()`. [`stdlib_field_casts`](../compiler/noirc_driver/tests/stdlib_field_casts.rs) checks these conversion boundaries.

The `Hash` and wrapping arithmetic impls for wide integers preserve their BN254 implementations and supply integer fallbacks for other fields. Hashing writes 32-bit limbs; wrapping addition and subtraction avoid overflow through comparisons; wrapping `u128` multiplication combines 64-bit limbs. See [`hash`](../noir_stdlib/src/hash/mod.nr) and [`arith`](../noir_stdlib/src/ops/arith.nr).

`Field::lt` uses the BN254 implementation under that field and canonical byte comparison elsewhere, sized to the configured modulus. The embedded curve and Poseidon2 module are BN254-only. The derive registry uses a non-cryptographic multiply-add hasher for its comptime map.

# The width-generic standard library

`Add`, `Sub`, `Mul`, `Div`, `Rem`, `Neg`, bitwise traits, `Eq`, `Ord`, and `Default` have generic implementations for integer families. Inherent `max_value`, `min_value`, and `bits` derive their results from the width. Primitive operators already support these widths; the trait impls make them usable in generic functions.

`Hash`, `From`, `AsPrimitive`, and wrapping arithmetic retain their explicit width lists. [`stdlib_elaboration`](../compiler/noirc_driver/tests/stdlib_elaboration.rs) executes numeric trait and limit checks under each configured field, verifies Goldilocks arithmetic, hash limbs and comparison fallbacks, and checks cryptographic API gating.

# Entry-point values: one field element per scalar

The ABI carries every scalar (`Field`, integer, `bool`) in exactly one field element (`AbiType::field_count`), so a value crosses the entry point only if its element is below p. An entry point's integer types are a fixed list, bounded by the field. First, a parameter or return of `main` or of a contract function, including one nested in an array, tuple, struct or alias, must be one of the lowerable types, `u8` through `u128` and `i8` through `i64` (`is_lowerable_integer_width`): the `Prover.toml` input language is that list and not "any width below the modulus", so a `u24` or `u253` that is legal inside a program is refused at `main` under every field (`IntegerNotLowerable`, whose diagnostic spells the list out), and a wider or narrower value is widened or narrowed inside the program. This is the subset Mavros lowers today; it keeps `Prover.toml` readable as concrete types and can be widened later without breaking a program. Second, a lowerable type is refused when its width is the bit length of the modulus or more (`FieldConfig::fits_unsigned`), signed and unsigned alike, because a signed value crosses as its unsigned bit pattern. Under Goldilocks that leaves `u8`, `u16`, `u32`, `i8`, `i16` and `i32`, so `u64`, `i64` and `u128` are refused; under BN254 and BLS12-381 all nine cross; `Field` and `bool` are unaffected. The rule is part of `program_validity` in [`validity`](../compiler/noirc_frontend/src/hir_def/types/validity.rs), reported as `InvalidTypeForEntryPoint` whose innermost cause is `IntegerNotLowerable` or `IntegerExceedsField`, and it is decided on the type, before any value exists: accepting the type and refusing only the values whose pattern reaches p would let a program compile under a field and then fail per value when it runs, while a refusal on the type can later be loosened without breaking a program. An entry point cannot be generic, so a width that a struct's generic argument, an alias, a global or an arithmetic expression spells out is already a number when the signature is elaborated and is refused there. Test and fuzz functions, `#[fold]` functions and `#[abi(tag)]` globals are not bounded: no field element carries their values across a proving boundary, and a tag carries an integer's magnitude. An `#[export]` function is outside the rule as it is outside `program_validity` altogether: `NoirFunction::is_entry_point` names only `main` at the crate root and a contract's entry points. [`field_contract`](../compiler/noirc_frontend/src/tests/field_contract.rs) pins the rule under every field (`entry_point_integers_are_the_lowerable_types`, `entry_point_integers_must_fit_below_the_modulus`, `the_entry_point_rule_looks_through_every_aggregate`, `the_entry_point_rule_leaves_other_functions_alone`, `contract_functions_follow_the_entry_point_rule`, `the_entry_point_diagnostic_lists_the_lowerable_types`, `the_entry_point_diagnostic_names_the_field_and_the_widest_width`); `entry_point_width_u24` in `test_programs/compile_failure` pins nargo's output.

The codec that carries values across the boundary has three layers, so that a consumer other than the circuit backend chooses the field at run time. `Format::parse` in the [input parser](../tooling/noirc_abi/src/input_parser/mod.rs) reads TOML or JSON inputs under a `FieldConfig` its caller passes; `encode_scalar` and `decode_scalar` in [`scalar`](../tooling/noirc_abi/src/scalar.rs) convert between a scalar and its element under a `FieldConfig`, as the canonical integer in `[0, p)`; `Abi::encode` and `Abi::decode` build and read the backend's `WitnessMap<FieldElement>` and are linked-field by their type, so a field mismatch cannot be expressed there. A parsed value is held in `InputValue::Field`, whose linked element is an exact container for every field whose modulus is at most the linked one; a field with a larger modulus is refused before any value is read (`FieldNotCarried`), so one bn254 build parses bn254 and Goldilocks inputs, and bls12_381 inputs need a bls12_381 build (`a_field_the_linked_element_cannot_hold_is_refused`).

The value rule, applied by `scalar_to_field` in the input parser and by `decode_scalar`: an integer is accepted iff it lies in the range of its type **and** its unsigned fixed-width bit pattern is below p; a `bool` is `0` or `1`; a `Field` is any value below p, a negative native spelling denoting the negation of its magnitude in the selected field while a quoted spelling must be non-negative. Nothing is reduced at this boundary, so accepted signed values never collide modulo p, and a backend that reduces an integer return modulo p cannot serve as an oracle for one whose pattern reaches p (the type rule leaves a compiled program no such return). The type rule keeps a compiled program's inputs inside this domain; the value rule is what an ABI written by hand, or an `InputValue` built without compiling, meets: under Goldilocks a `u64` accepts exactly the values below p and an `i64` exactly `[-2^63, -2^32] ∪ [0, 2^63 - 1]`, because `-2^32` encodes as `p - 1` and `-1` as `2^64 - 1 ≥ p`. Refusals name the selected field and its modulus. `Format::parse` owns the check for both formats and for quoted and native spellings alike, because consumers other than `nargo` stop there and never reach `Abi::encode`; `find_type_mismatch` repeats the type-range half for callers that build an `InputValue` directly. The boundary vectors below pin the domain and `field_values_are_accepted_iff_below_the_selected_modulus` in the input parser pins the refusal's wording, under every field the build carries.

`boundary_vectors` in [`conformance`](../tooling/noirc_abi/src/conformance.rs) supplies shared accept and reject cases for the ABI parser and ast-interpreter's `Prover.toml` bridge: `p - 1`, `p` and `p + 1`, the 64-bit values on either side of the Goldilocks modulus, the widest width the parser carries (one bit short of the modulus, which a hand-written ABI can still name) and one bit wider, and spellings each scalar type refuses. `the_parser_accepts_and_refuses_exactly_the_boundary_vectors` pins the parser to them.

`FieldConfig::num_bytes` rounds a modulus up to whole 64-bit limbs and sets the padding for `FieldValue::to_hex` and ABI tags. Signed `InputValue` serialization uses the linked element's width, even when its value was parsed under another field; JSON serialization of unsigned and `Field` values trims leading zeroes. For the linked field, `num_bytes` agrees with the element's hex width (`every_boundary_value_agrees_with_the_linked_field_element`).

A multi-element encoding for integers wider than the field is a separate, versioned policy to be agreed with the consumers of the monomorphized AST (signedness, limb width and order, element count, version). The field's properties do not pre-commit it: there is no "elements per integer" property anywhere in the compiler.

# Run-time field configuration

[`FieldId`](../acvm-repo/acir_field/src/field_config.rs) names a supported field: `bn254`, `goldilocks`, and `bls12_381`. Its discriminant is the wire code, decoded only through the checked `from_code`, and it has no `Default`, so a field is always named deliberately. `FieldConfig` holds an id and answers every question the front half asks about its field (`modulus`, `num_bits`, `fits_unsigned`, whether a `width`-bit unsigned type is carried in one element, and `matches_field_attribute`) from rows written out in that file, deliberately not from the `FieldElement` alias the crate is built with, so a bn254 build answers Goldilocks queries. Each row-dependent accessor is an exhaustive `match` with no fallthrough arm, so a new field is a compile error until it has a row (`every_row_states_its_modulus_and_width`), and `the_linked_row_agrees_with_the_linked_field_element` pins the row of the built field to the linked element under whichever field the crate is built with. Two rules keep the front half field-generic: a layer only asks the configuration (modulus, width, whether a width fits) and never names a field or compares against a width literal; and a layer never uses `FieldElement` as the carrier for a value that is not semantically a `Field`.

The configuration is seeded once per compilation. It travels from `--field` on [`CompileOptions`](../compiler/noirc_driver/src/lib.rs) through `FrontendOptions` into the [`NodeInterner`](../compiler/noirc_frontend/src/node_interner/mod.rs), the one object every pass from definition collection to monomorphization holds, at the first elaboration entry point (`collect_defs_and_elaborate` and `Elaborator::new`); a query before that, or a second seed with a different field, is an internal error. Definition collection, the literal lint, the cast rules, the comptime and monomorphization `modulus_*` builtins and the comptime cast widths all read `interner.field()`, and frontend tests compile and execute comptime code under any row in one build (`GetProgramOptions::for_field`).

The monomorphizer's `into_output` returns a `MonomorphizationOutput`: the program, the `FieldId` it was compiled under, and the source files it drew code from. The label travels beside the program, never inside it, and consumers must check it before lowering (`output_is_labeled_with_the_configured_field`).

# Comptime values carry their field

A comptime `Field` value is a [`FieldValue`](../acvm-repo/acir_field/src/field_value.rs): a canonical representative in `[0, p)` together with its `FieldId`. `Integer::Field` uses this carrier for interpreter evaluation and type-level arithmetic. Operations reduce modulo the configured field; mixing fields is an internal error. Native integer variants keep their checked arithmetic.

Tests compare arithmetic, formatting and signed conversions against the linked `FieldElement` at random and boundary values. BN254 hashing also stays compatible because compile-time reflection exposes it. Signed conversions choose by bit length; `Display` chooses by decimal length. The linked-element helpers in [`integer`](../compiler/noirc_frontend/src/hir/comptime/integer.rs) remain for SSA lowering and the fuzzer. `FieldValue::from_linked_element` converts values coming from linked carriers such as the ABI parser.

# Builtin capabilities

`FieldConfig::embedded_curve` and `has_poseidon2_permutation` control the comptime crypto builtins. BN254 supports both; other fields return `Unimplemented`. The solvers use explicit bn254 elements, independent of the compiler's linked field. `poseidon2_config_state_size` still returns bn254's width; fencing this stdlib dependency remains future work. Compile-time hashes are reduced into the configured field and need not agree across fields.

The ECDSA foreigns, `ecdsa_secp256k1` and `ecdsa_secp256r1`, are bytes in and a `bool` out and carry no field at any plane: the comptime interpreter, the ACVM and the Brillig VM dispatch them to the `k256`/`p256` solvers without a field element, so they run under every configured field. On Mavros they are rewritten into vendored Noir over 120-bit limbs, which needs a field of roughly 247 bits or more, so at run time they are bn254-only there; a Goldilocks ECDSA is a prime-field library on native wide integers, not a builtin, a flag or a `FieldConfig` member, since `#[field]` gating and a width `static_assert` already select a per-field implementation inside one crate. `keccakf1600` has no Mavros replacement under any field.

# The backend boundary

`ensure_field_is_linked` in [`noirc_driver`](../compiler/noirc_driver/src/lib.rs) rejects unsupported fields before circuit compilation, including cached artifacts. The same guard protects `nargo execute --force-comptime`, `nargo interpret` and the SSA-impact example, which read their inputs in, and evaluate with, the linked field. `check_crate` accepts any configured field, the standard library included.

ABI-tagged globals preserve canonical `Field` values and native integer magnitudes. Hex output is padded to the configured element width; wider integers retain their full magnitude, and signed integers carry their sign separately (`abi_tag_integers_preserve_sign_width_and_magnitude`).

The `bn254`, `bls12_381` and `goldilocks` features of [`acir_field`](../acvm-repo/acir_field/src/lib.rs) select the built field and are mutually exclusive (`assert_unique_feature!`), so enabling two is a compile error rather than a silent pick; `FieldId::linked` is the one place the front half reads them. Every crate that reaches the field through the `FieldElement` alias, including [`noirc_abi`](../tooling/noirc_abi/Cargo.toml), forwards a `goldilocks` feature to it. Field element conversions are width-agnostic: `to_i128` reads the shorter of an element's two spellings, on the 8-byte Goldilocks representation as on bn254's 32 bytes (`test_to_i128_roundtrip` and its `goldilocks` twin in [`field_element`](../acvm-repo/acir_field/src/field_element.rs)).

`nargo_cli` and the wasm crates hard-enable `bn254`, so the Goldilocks build is exercised by [its own workflow](../.github/workflows/goldilocks.yml): it builds `noirc_driver` with the feature and runs what only that build can check, the field crate's arithmetic, the configuration row and the run-time carrier against the linked element, the ABI crate whose parsed values and witnesses live in the linked element, the driver's boundary rule and the programs it compiles under the linked field, and the SSA probes in [`small_field_validation`](../compiler/noirc_evaluator/src/ssa/interpreter/small_field_validation.rs). The frontend field-contract tests select every field in the default build; other frontend tests run with the linked field. A change to feature-gated code is covered only if a test runs there; the default build proves nothing about it. [The fork-residual workflow](../.github/workflows/fork-residual.yml) compares the fork's diff against the upstream release named in `.github/fork-base.txt` with the committed `.github/fork-residual.txt`, so a file enters or leaves the fork's residual only together with the manifest.

# Checking the two fields against each other

The monomorphized AST is the surface compared across fields: integer, boolean and structural results must agree exactly and only `Field`-typed values may differ; a panic or internal error under either field never passes. The [ast-interpreter](https://github.com/worldfnd/ast-interpreter) executes the AST under both fields, in one build of a pinned compiler revision, since the compiler, the input parser and its own values all take the field at run time, and records the comparison per program in its committed `STATUS.md`.

# Intended direction

The SSA interpreter's numeric values follow the configured field, which lets `nargo interpret` and `nargo execute --force-comptime` run under any field; a second arithmetic backend makes the back half itself field-generic and width-generic, at which point neither boundary rule has anything left to refuse. A versioned multi-element encoding lets integers wider than the field cross an entry point.
